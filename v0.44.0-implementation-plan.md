# v0.44.0 implementation plan

Status: planned. Predecessor: `0.43.3`. Release type: measured limits and maintenance.
Delivery order and shared release gates are in the [roadmap](ROADMAP.md).
Source: F17 and the performance, maintainability, and documentation programs
in the [assessment](pg-react-assessment.md). Retain F10 and F18 regressions
from the two preceding patches.

## Outcome and boundary

Publish an operating envelope for the corrected runtime, including latency,
backlog, retention, and recovery limits. Remove comparison work that grows with
unrelated historical state. Make current SQL definitions and qualification
readable without reconstructing historical rename chains.

Complete [v0.43.2](v0.43.2-implementation-plan.md) and
[v0.43.3](v0.43.3-implementation-plan.md) first. Their source authorization,
fact snapshot, failure isolation, and restore behavior define the semantics to
measure. Performance changes must preserve those exact results.

Keep the existing worker model and dependency set. Do not add parallel workers,
cached backlog counters, a new scheduler, speculative indexes, or new policy
semantics. A measured limit is a valid release result when an optimization does
not justify its complexity. Do not broaden platform or RLS support through a
benchmark claim.

## Implement the release

### 1. Establish the baseline and benchmark contract

Add a small current benchmark runner using the existing Docker, SQL, pgbench,
and JSON evidence patterns. Keep dataset generation deterministic through named
seeds and explicit timestamps. Reuse existing tooling rather than adding a
benchmark service. Record exact source revision, image digest, dependency
versions, CPU, memory, disk, PostgreSQL settings, and dataset dimensions.

Use the following matrix as a set of named workloads, not a full Cartesian
product. Run one-factor sweeps from a published baseline, then the combined
stress cases listed below. State which combinations were actually measured.

| Dimension | Required cases |
| --- | --- |
| Rules | 1, 10, and 100, with shared and independent sources |
| Matches | 1,000, 10,000, and 100,000 for the selected target workload |
| Changed facts | 0%, 1%, and 10% per refresh |
| Source shape | Simple filter, keyed join, nested view, and wide row |
| Work | Empty queue, steady load, sustained backlog, and retry-heavy load |
| Contention | Independent keys, one hot conflict key, and mixed agenda groups |
| Consequence | Fast database write, slow database write, failing consequence, and outbox |
| History | Fresh state and retained history before and after pruning |
| Recovery | Worker loss, expired leases, source drift, and replacement while draining |
| Review | Evidence limits 1 and 100, large targets, and growing unrelated state |
| Packages | Simple chain, the 61-node layered DAG, and maximum permitted graph size |

Combine sustained backlog with a hot conflict key, retries with worker loss,
and retained history with comparison and restore. Include both many rules with
few matches and few rules with many matches. These cases exercise different
costs even when total match counts agree.

Run one warm-up and at least five measured repetitions per workload. Collect
enough per-operation samples to report p50, p95, and p99 honestly; retain sample
counts and omit a percentile when the run cannot support it. For destructive
recovery trials, report every trial and the range as well as the median.

Record fact-to-result and fact-to-effect latency, refresh duration, completed
work throughput, frontier lag, lock waits, WAL bytes, dead tuples, buffer reads,
temporary I/O, disk growth, pruning cost, and recovery time. Record available
memory metrics with their measurement scope. Do not label process RSS as exact
query memory. Retain errors and timeouts as results, not discarded samples.

Gate: the `0.43.3` baseline can be regenerated from the recorded command and
seed, with full semantic output matching the correctness fixtures. No speedup
or supported capacity is claimed before the candidate has matching measurements.

### 2. Remove unrelated state from production comparison

Trace every consumer of the before/after authoritative checksum, including M35
counterfactual comparison and captured evidence. Move whole-state no-effect
checks into tests, where they remain useful correctness oracles.

Use target-specific declaration/version identity, dependency fingerprints, and
frontier or snapshot metadata for production provenance. Do not call a scoped
fingerprint an authoritative database checksum. Publish a new evidence contract
version when meaning or fields change. Keep old persisted evidence readable
under its original version and document how clients distinguish the two.

Make the compatibility decision explicit before editing output. Preserve valid
ordinary calls. If an existing checksum field cannot keep its meaning at bounded
cost, expose the new evidence version additively and deprecate the old contract
with a migration example. Do not silently replace a full-state checksum with a
target digest in the same field.

Combine source validation scans where their semantics permit it. Evaluate one
source snapshot through the shared safe evaluators, aggregate total, null-key,
and duplicate-key checks together where possible, and collect limited evidence
without repeated full materialization. Reuse validated uniqueness only while
its schema and source assumptions remain valid. Do not turn an exact count into
a sample without an explicit incomplete result.

Separate response limits from execution budgets. Preserve `evidence_limit` as
an output bound. Define caller-set statement timeout, target size, temporary
storage, and concurrency settings for the supported review workload. Set timeout
before the statement starts. A server cancellation returns an error and leaves
no durable effects; it cannot be reported as a complete empty comparison.

Gate: hold the target fixed and grow unrelated work and activations through
0, 10,000, and 1,000,000 rows. Compare complete semantic results, record query
plans and buffers, and prove the new production path does not scan or aggregate
unrelated runtime tables for provenance. Keep M34 and M35 full-state no-effect
assertions in tests. Measure p95 and temporary I/O against the baseline rather
than assuming that a smaller response means a cheaper query.

### 3. Optimize only the measured runtime bottlenecks

Profile no-change `sync_semantic_keys` cycles and their `last_seen_at` writes.
Trace retention and reconciliation consumers before skipping a timestamp update.
If the timestamp is required for correctness, retain it and publish its cost.
If unchanged rewrites serve no consumer, remove them and verify identical key,
activation, and recovery behavior while measuring WAL and vacuum effects.

Measure the before/after agenda counts in `managed_cycle`. Prefer an existing
scoped query or index when it answers the same question. Do not replace exact
state with a cached counter that requires a new reconciliation mechanism.

Capture `EXPLAIN (ANALYZE, BUFFERS)` for global and per-version claim selection
under retry-heavy, blocked, conflicting, and multi-version backlogs. Eliminate
redundant candidate scans only when ordering and fairness remain unchanged.
Add or change an index only when measured plans justify it, including the cost
of inserts, state updates, retention, and restore.

Gate: every optimization has a before/after workload, identical full state and
effects, and recorded read, write, and latency costs. Preserve hot-key exclusion,
barriers, draining-version progress, and lease fencing. If a candidate worsens
the relevant workload without an accepted tradeoff, leave it out of the release.

### 4. Separate current definitions from release history

Freeze all published migration and installation files. Add a deterministic
assembly command with an explicit ordered input list. Use concatenation and
catalog queries rather than a custom SQL parser. First prove that historical
ordered concatenation reproduces the predecessor artifact byte for byte.
Check the later extraction separately for catalog and behavior equality;
effective definitions will not reproduce bytes containing historical rewrites.

Create planned `sql/current/` modules grouped by authorization, declaration
planning, comparison, lifecycle, execution, packages, and diagnostics. Extract
effective definitions from a pinned installed database and review them against
their historical sources. Include types, relations, sequences, defaults,
indexes, constraints, triggers, grants, ownership, extension configuration
registration, and required seed rows in dependency order. Keep compatibility
delegates explicitly classified.

Make these modules the authored definitions used by the new installation and
upgrade assembly. Keep state migrations explicit and separate from definition
replacement. Split extraction commits from behavioral changes so an extraction
must produce an identical normalized installed catalog and behavior transcript.
Do not require an unrelated rename of every internal milestone-prefixed symbol.

Generate a lookup map from exact current signature to source module, installed
definition, public or internal classification, and historical delegates. Use
explicit rename metadata where catalog dependencies do not record PL/pgSQL
calls. The map must identify those limits rather than claim a complete static
call graph. Every public API inventory entry must resolve to a definition.

Replace new uses of `pg_get_functiondef` plus textual substitutions with explicit
definitions. Leave published migrations untouched. For an unavoidable existing
rewrite on a supported upgrade path, assert the expected original text,
substitution count, and exact resulting definition.

Gate: two assemblies produce identical bytes. Fresh install and populated
adjacent update have identical expected definitions, signatures, privileges,
volatility, security properties, and exact behavior. The lookup map resolves
current public APIs and their compatibility delegates without manual archaeology.

### 5. Organize qualification by behavior and publish limits

Add a canonical current runner, planned as `tests/qualification.sh`, with fast
static and complete database profiles. Compose existing scripts into named
behavior groups: authorization, deployment, comparison, lifecycle, execution,
packages, recovery, and artifact identity. Keep historical release runners for
their pinned releases. Avoid copying every old fixture into a new milestone file.

Use one release manifest for the current version, predecessor, image identity,
and profile selection wherever the existing tools can consume it directly.
Keep semantic assertions for those values. Preserve the scheduled and failed-run
evidence behavior established by `0.43.3`.

Add a small deterministic cost-regression subset to ordinary qualification.
Run the full benchmark matrix on a pinned measurement runner for release
qualification. Record proposed latency and recovery acceptance ceilings in the
workload manifest before evaluating the candidate. Derive them from the baseline
and intended workload requirements, with runner noise documented. Do not invent
a universal throughput threshold or change a failed ceiling after the run
without recording the decision and rerunning qualification.

Publish `docs/benchmarks.md` with commands, datasets, hardware, raw artifact
references, plots, and interpretation. Update `docs/limits.md`,
`docs/support-matrix.md`, `docs/operations.md`, `docs/backup-restore.md`, and
`docs/known-limitations.md` with the measured envelope. State unsupported and
unmeasured cases separately. Include sustained overload behavior, frontier lag,
retention growth, stopped-backup duration, and restore time.

For each supported workload, name the tested size, rate, configuration, latency
range, and recovery procedure. Make retained-history and no-change costs visible.
Do not extrapolate one machine's result into a universal production guarantee.

## Exit gates

- F17 is closed for the new evidence contract, with explicit compatibility for
  old output and persisted evidence. No global no-effect checksum remains in
  the new production comparison path.
- All correctness and recovery gates from `0.43.2` and `0.43.3` still pass.
- Current SQL assembles deterministically and has a verified signature-to-source
  map. Fresh and upgraded installations agree on the full expected catalog.
- The required benchmark workloads finish with retained results or become
  explicit unsupported limits. Missing evidence cannot count as a supported case.
- Supported sizes, rates, latency, retention, and recovery claims cite reproducible
  candidate measurements. No unmeasured performance percentage appears in release notes.
- Canonical current qualification runs locally, on schedule, and for release
  publication against the same image. Historical evidence remains pinned.
