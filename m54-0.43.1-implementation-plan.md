# v0.43.1 implementation plan

> **Status:** Proposed implementation plan
> **Release target:** extension `0.43.1`
> **Release type:** M54 correctness and qualification closure
> **Predecessor:** M54, extension `0.43.0`

## Outcome

Ship a patch that closes the unfinished M54 correctness and qualification work.
The patch adds no new policy capability. It makes standalone deployment safe
under concurrent changes and makes the released API, documentation, and
qualification evidence match their claims.

The release is complete when an operator can review a standalone rule or
decision, wait behind another deployment, and receive either the exact
reviewed result or a stale-plan error. The release must also prove command-rule
replacement with pending, leased, and retrying work, and must leave a complete
old or new deployment after every injected replacement failure.

## Release boundary

`0.43.1` may change:

- standalone deployment serialization and stale-plan checks;
- the review-token binding for M54 ordinary deployment;
- SQL and shell qualification fixtures;
- the installed API inventory audit;
- current operational, installation, limitations, and support documentation;
- dependency auditing and evidence packaging;
- release metadata and adjacent migration artifacts.

`0.43.1` must not add a rule kind, a decision semantic, a temporal feature, an
RLS execution mode, a workflow engine, a new scheduler, or a supported-scale
claim. M59 remains a later measurement release.

Preserve all valid `0.43.0` calls. Keep the legacy JSON-precondition overload
and its legacy digest behavior. Keep compatibility and advanced APIs installed.
The adjacent update must not mutate deployments, source rows, parameter rows,
work rows, or policy packages by itself.

## Main correction: plan after the deployment lock

`pgreact_internal.m54_deploy()` currently validates and previews before it takes
the per-target advisory lock. It then uses the old action, source identity, and
work state after the lock. A second transaction can change the target while the
first call waits, so the first call can report `KEEP` or replace a declaration
that it did not review.

Use this order for every standalone M54 deployment:

```text
validate immutable input
    -> acquire the per-target advisory lock
    -> read the current declaration, source, barrier, and work state
    -> compute the authoritative M54 preview and plan
    -> compare the review token with that locked plan
    -> deploy, keep, or reject within the same transaction
```

Implement the correction in `sql/m54.sql`, then generate and check the
`sql/pg_react--0.43.0--0.43.1.sql` and `sql/pg_react--0.43.1.sql` artifacts.
Keep `m54_preview()` as the single plan shape. Refactor the deploy path so no
mutable value that contributes to `action`, `old_work_required`, source
fingerprints, declaration identity, or barrier state comes only from a
pre-lock preview.

For a reviewed call:

1. Validate the declaration and token shape before taking the lock.
2. Take the same target lock used by replacement and removal.
3. Read the current declaration row with `FOR UPDATE` and reread all source,
   barrier, and work state used by the plan.
4. Recompute the M54 preview and `plan_digest` from that locked state.
5. Reject the call if the token target, declaration digest, or `plan_digest`
   does not match the locked plan.
6. Recheck ownership and package ownership against the locked row.
7. Apply the operation only to the delegated object identified by the locked
   row.

The M54 `plan_digest` is the reviewed identity for every M54 ordinary rule,
decision, and policy-set deployment. `pgreact.review_token()` must not select
`preview_digest` for ordinary rules or decisions. The old JSON-precondition
overload may continue to accept the legacy preview digest so existing callers
remain compatible.

If work becomes pending, leased, or retryable after review, the locked plan
must invalidate the token because its work state changed. A fresh review may
proceed only after the caller supplies the required `DRAIN_OLD` or `CANCEL_OLD`
policy. Deployment must never infer that policy.

## Workstream 1: close the serialization and token gap

Update the M54 deployment implementation and its generated SQL artifacts.

Acceptance criteria:

- A reviewed `KEEP` fails with `M54_REVIEW_TOKEN_STALE` when another session
  replaces or removes the target before the waiting call acquires the lock.
- A reviewed `REPLACE` cannot apply to a newly committed declaration or a
  different delegated object.
- A source DDL change, source fingerprint change, barrier change, or relevant
  work transition invalidates the reviewed plan.
- An unchanged deployment still returns the exact M54 `KEEP` result.
- Replacement still requires an explicit old-work policy when the locked plan
  reports eligible command work.
- A failed replacement leaves the complete old deployment active and leaves no
  active orphan object.
- Existing JSON-precondition deployment calls retain their current output and
  error contract when the caller does not use a review token.

Do not add a second planner. Reuse `m54_preview()`, the existing authoritative
replacement functions, and the existing target lock order.

## Workstream 2: qualify the risky deployment paths

Extend `tests/m54.sql` and `tests/m54.sh` with exact output assertions. Add one
focused two-session harness if the current shell lane cannot keep session
coordination readable. The harness must use the candidate image and must record
the SQL output as evidence.

Cover these cases:

- concurrent reviewed `KEEP` versus replacement;
- concurrent reviewed `KEEP` versus removal;
- concurrent reviewed `REPLACE` versus replacement;
- a source DDL change while a deployment waits for its lock;
- work changing from none to pending, leased, or retry-wait after review;
- standalone command-rule replacement with no old work;
- standalone command-rule replacement with pending work;
- standalone command-rule replacement with leased work;
- standalone command-rule replacement with retry-wait work;
- successful `DRAIN_OLD` replacement;
- successful `CANCEL_OLD` replacement;
- omitted and malformed old-work policies;
- wrong target, wrong declaration, stale token, malformed token, and oversized
  token;
- owner, operator, reader, and unauthorized deployment attempts.

Each concurrency case must control the lock holder and waiter explicitly. It
must assert the complete returned JSON after removing only run-specific values
such as timestamps or generated UUIDs. Counts alone are not sufficient.

Add transaction-local failure injection for the replacement path without adding
a public API or an inventory entry. Inject failure after each meaningful phase:

- validation;
- target resolution;
- current declaration load;
- replacement planning;
- old-work check;
- source verification;
- consequence verification;
- generated object creation;
- binding or catalog update;
- active-version cutover;
- history or audit write;
- cleanup.

For every injected failure, assert the full old deployment state, the absence of
an active hybrid, and the absence of an active orphan generated object. Keep the
failure hook private and transaction-local so a test cannot change production
behavior through a public call.

Keep the inherited M38 through M54 checks. Make the complete lane run the new
fixtures, fresh install, populated `0.43.0 -> 0.43.1` update, and
rollback-by-restore.

## Workstream 3: audit the installed API catalog

Turn `tests/api-inventory.sh` from a checked-in JSON comparison into a catalog
audit against the candidate database.

The audit must:

- start or connect to a database running the candidate image;
- enumerate public `pgreact` and `pgreact_api` functions and relations from
  `pg_proc`, `pg_class`, and `pg_namespace`;
- record function identity arguments, return type, volatility,
  security-definer state, and relevant ACLs;
- record relation kind and relevant ACLs for public views and tables;
- compare the installed result with `docs/api-inventory.json`;
- fail on any public object that is not classified;
- fail on any classified object that is missing, has a different signature, or
  has a different security property;
- preserve the explicit exclusion of `pgreact_internal` objects.

Do not classify by broad prefixes. Use explicit object entries or an explicit
allowlist for each public schema. A new public object must force a deliberate
classification decision.

Classify `pgreact.policy_set` and its complete package constructor as ordinary.
Keep support declaration constructors that are not part of the normal safe
change path under the chosen advanced classification. Document that decision
in the inventory and the human API reference.

Run the static JSON checks as a fast preflight, then run the catalog audit
against the built image in the canonical qualification workflow. Keep
`docs/m54-api-inventory.json` as the milestone record only if it matches the
installed current inventory; otherwise update it as part of the release work.

## Workstream 4: restore useful current documentation

Keep neutral current paths canonical. Move the useful content from historical
guides into the current guides and remove historical framing from the copied
sections.

Update these current documents:

- `docs/operations.md`: managed-worker failure, backlog diagnosis, stale
  leases, source and declaration drift, recovery barriers, retention, and
  restore procedures;
- `docs/installation.md`: exact `shared_preload_libraries`, pg_trickle
  scheduler settings, worker roles, isolation, polling, and restart steps;
- `docs/known-limitations.md`: RLS-backed evaluation is outside the qualified
  boundary, along with the current comparison and delivery limits;
- `docs/support-matrix.md`: an environment matrix plus feature rows for
  ordinary deployment, replacement, command work, policy packages, RLS,
  comparison bounds, recovery, and delivery guarantees;
- `docs/limits.md`: structural limits and explicit `unavailable` values where
  the product has not measured a cost faithfully;
- `README.md`, `docs/index.md`, and the current API reference: links and
  classifications for `0.43.1`.

Do not copy the historical guides as a second current version. Keep the old
`v1-*` files reachable from History and label them as historical records.
Update `docs/current-release.json`, the current-doc audit, release notes, and
the adjacent migration guide to `0.43.1` and `0.43.0 -> 0.43.1`.

## Workstream 5: restore and tighten release evidence

Update `.github/workflows/qualification.yml` and `.github/workflows/release.yml`.

The reusable qualification workflow must:

- run `cargo install cargo-audit --version 0.22.2 --locked && cargo audit`;
- build the candidate image before the installed API catalog audit;
- run the concurrency, command-work, and failure-injection fixtures;
- run the current-doc, workflow, and static API audits;
- record the exact candidate commit and image digest;
- produce one evidence entry for every executed or inherited qualification;
- include a SHA-256 digest for every evidence artifact;
- reference inherited evidence by its exact immutable release or artifact
  digest;
- fail if an inherited artifact is missing or if the workflow would synthesize
  a placeholder path.

Generate `evidence-manifest.json` only after all logs and the candidate image
archive exist. Each entry must contain its mode, artifact reference, and
artifact SHA-256. The image archive, checksums, SBOM, and attestations must
refer to the image that passed the same workflow run.

The release workflow must publish only after the reusable qualification job
passes for the exact `v0.43.1` commit. Update all release identity checks,
artifact names, image tags, release notes, and the unpublished-release check.

The release must assert that `docs/m54-final-checklist.md` has no unchecked
required item. Mark the checklist complete only after the candidate evidence
exists. Keep the checklist as a release record, not as a plan that can remain
unchecked after publication.

## Implementation sequence

### Phase 0: freeze the patch contract

Record this plan and the patch scope. Do not start M59, M58, M45, or another
semantic milestone during the patch work.

### Phase 1: fix locked-plan deployment

Refactor `m54_deploy()` and `review_token()` in `sql/m54.sql`. Add the adjacent
upgrade and fresh-install SQL artifacts. Preserve the legacy JSON-precondition
overload.

Gate: standalone plan computation and token comparison occur after the target
lock, and the old M54 SQL corpus still passes.

### Phase 2: add exact race and failure fixtures

Extend the M54 qualification lane with two-session races, command-rule work
states, both old-work policies, and failure injection.

Gate: every race either completes the reviewed operation against the reviewed
state or returns the documented stale error. Every injected replacement failure
leaves the full old deployment active.

### Phase 3: implement the installed API audit

Generate the catalog view from the candidate database and compare it with the
explicit inventory. Classify `pgreact.policy_set` as ordinary and remove broad
prefix fallthrough.

Gate: the audit detects a missing object, a new unclassified object, a changed
signature, a changed ACL, a changed volatility value, and a changed
security-definer value.

### Phase 4: restore current runbooks and support claims

Move the needed operational and installation detail into the neutral current
documents. Restore the RLS limitation and the feature support matrix. Update
the current release manifest and all current-version assertions.

Gate: the current-doc audit passes, and the canonical install, replacement,
failed-work, and recovery journeys contain no `pg_sleep` or UUID lookup.

### Phase 5: unify patch qualification and evidence

Add `cargo audit`, move the installed API audit after image build, add artifact
hashes, and reject synthetic evidence. Run the reusable workflow on an
untagged `0.43.1` candidate first.

Gate: the candidate has one green qualification result and a complete,
hash-addressed evidence manifest.

### Phase 6: qualify and publish `0.43.1`

Run the exact candidate through fresh install, populated adjacent update,
rollback-by-restore, inherited qualification, the complete M54 lane, the
installed catalog audit, documentation audits, dependency audit, image checks,
SBOM, checksums, and attestations.

Gate: tag and publish only the commit whose reusable qualification passed.

## Exit gates

`0.43.1` is ready to tag only when all of these conditions hold:

- the locked-plan race is fixed in the shared M54 deployment path;
- M54 review tokens bind to the locked `plan_digest` for every ordinary kind;
- KEEP, REPLACE, removal, source DDL, and work transitions have exact
  two-session evidence;
- every replacement failure injection leaves a complete old deployment;
- standalone command-rule replacement exercises pending and leased work with
  both old-work policies;
- the installed catalog matches the explicit API inventory and no public object
  falls through an implicit classification;
- `pgreact.policy_set` is classified as ordinary;
- current installation and operations guides contain the required runbooks;
- the RLS limitation and actual feature support matrix are current;
- `cargo audit` passes in the reusable qualification workflow;
- evidence entries have artifact hashes or immutable inherited references;
- the checklist has no unfinished required item;
- fresh install, adjacent update, rollback restore, and inherited qualification
  pass for the exact candidate commit;
- the release job publishes the image that the qualification job tested.

## After the patch

Use `0.43.1` as the first stable design-partner baseline. Collect evidence on
real rule counts, matches, change rates, work backlog, retries, package size,
comparison size, WAL, storage, retention, restart, restore, reconciliation,
and recovery time before selecting the next milestone.

Choose M58 first only if a real prospective user needs RLS or another
authorization-context feature. Otherwise choose M59.

M59 should measure operating boundaries rather than add a performance feature.
Publish curves for rules, matches, fan-out, reevaluation, cascade depth,
lifecycle churn, work throughput, decision subjects and candidates, package
replacement, comparison size, catalog growth, WAL, retention, restart, backup
and restore, reconciliation, and sustained overload. Test both workloads with
many rules and few matches and workloads with few rules and many matches.
Include no-change cycles and bursty command work. Compare comparison cost with
production evaluation cost. Report backpressure, latency growth, or failure
under sustained overload. Report a field as `unavailable` when it cannot be
measured faithfully, including memory and temporary-storage cost. Do not fill
the current comparison cost placeholders with synthetic numbers.

Do not start M59 before the `0.43.1` field-evidence period ends, unless a real
RLS blocker selects M58 or a new safety issue selects M55 or M56.
