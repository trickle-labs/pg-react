# v0.50.0 — Joint rollout and supported operating envelope

> **Status:** Proposed; first cohort admission is gated, not automatic  
> **Predecessor:** `0.49.0`  
> **Source milestone:** R5 — Joint rollout, intentionally before optional R4  
> **Budget:** 30 person-days / six person-weeks  
> **Owners:** Joint release/qualification owner, adapter owner and operator; MDM owner signs business-control evidence; independent reviewer signs go/no-go

[Roadmap](../ROADMAP.md) · [Common release gates](../docs/planning/RELEASE-GATES.md) · [Evidence and sources](../docs/planning/EVIDENCE.md)

## 1. User-visible outcome

The first named cohort has a reproducibly qualified optional stewardship integration for routing, due-date control and bounded escalation. Operators can inspect backlog and domain outcomes, pause safely, recover a populated deployment, and determine whether the workload remains inside its measured operating envelope.

This is not a general-production claim across all MDM configurations, tenants or data volumes. The source's first-release success is a case being routed and escalated safely while humans retain stewardship authority; approvals remain independently opt-in. [S0 §8]

## 2. Entry gates and named workload

All mandatory 0.46.0–0.49.0 behavior must be installed and qualified on real PostgreSQL, pg_trickle, React and MDM artifacts. The exact MDM intent contract and public projection must exist; tests that imitate an MDM API cannot replace this dependency.

Run this release with MDM M4. The starting baseline is pg-trickle `0.105.2` plus MDM `0.11.0`; the final manifest must identify the actual later MDM artifact containing M1/M2. Requalify any dependency change after R0. Include upstream's deferred soak/long-running limits in the cohort decision instead of claiming that `0.105.2` supplies longevity evidence. [S8, S9]

Before qualification begins, nominate a workload owner and capture representative case categories, queues, service-window policy, escalation levels, concurrency, manual-edit patterns, expected arrival/churn, retention requirements and recovery objectives. Identify a small cohort using a reviewed stable predicate or explicit membership set.

All observation and soak periods are declared in the qualification manifest. Engineering to run/analyze them is included in the six-week effort budget; passive elapsed observation time is not claimed to equal person-weeks. Do not attach a release date until external readiness and the observation window are known.

## 3. Scope and exclusions

Deliver the cross-project acceptance suite, full fixed-population shadowing, a narrowly staged enablement procedure, public operational queries/dashboards, exact-artifact packaging, populated recovery/clone drills and measured operating limits.

Keep the first scope to one administrative domain and the qualified non-RLS projection. Exclude approval requirements, human voting, identity automation, network transport, Delta consumption, a generalized benchmark program for every pg-react feature, multiple platforms and unattended mass rollout.

If the named workload exposes a correctness or privilege defect, fixing or narrowing it takes priority over cohort expansion. Broad scale claims require separately approved evidence. The existing M59 work does not automatically qualify the new adapter/MDM combination.

## 4. Implementation design

### 4.1 Freeze a joint qualification manifest

Pin the exact image digests, extensions, contract digest, adapter package, platform, effective PostgreSQL version, isolation, CDC, coordinator ownership, temporal configuration and capability responses. Re-run all applicable common release gates against this final tuple, including inherited differential-refresh and ordinary-API regressions.

Classify each required test as passed/failed/blocked with retained real logs. Do not translate skipped Graph tests, synthetic MDM fixtures, or an empty evidence directory into successful qualification. Use a machine-readable manifest and derive the overall result from individual gates.

Maintain an explicit public-API inventory for the adapter. Prove that release packaging contains no mandatory MDM dependency in the core and that the exact qualified artifact is the one selected for publication.

### 4.2 Run the shared failure suite

Exercise duplicate execution, uncertain commit, concurrent human edits, evidence changes, recurring reviews, ambiguous/no routing candidates, time-only expiry, stale policy work, disabled bindings, missing capabilities, privilege rejection and publication failure.

Run cross-project restore, failed-upgrade recovery and clone launch procedures on populated databases. Compare complete immutable requests, receipt rows, control values, work outcomes, and published review rows with expected fixtures. Read MDM's documented pending-stewardship state, including successful no-change publication observations. An accepted control with delayed MDM publication must remain visible as accepted and must not be resent to force publication.

Test actual operator pause and restart steps using normal roles. Validate in-flight behavior at the acknowledged pause barrier. Review source and runtime observations to prove no consequence calls `mdm.refresh()` or a human approval API.

### 4.3 Shadow the complete fixed population

Start in read-only comparison mode. Capture a consistent reference population and policy versions, then cover it with bounded comparisons or an isolated qualification copy. Keep a coverage manifest that proves every intended case was examined exactly once at the chosen boundary. A `partial` result blocks complete-population sign-off.

Have the workload owner review would-be queue assignments, due dates, no-ops, protected cases and escalation plans. Record expected exceptions and manual handling; do not silently discard ambiguous results to improve agreement rates. Freeze the approved package/digest used for the cohort.

### 4.4 Staged enablement

Use these stages without bypassing their evidence:

1. **Installed, effects disabled:** verify admission, grants, contract and no-effect core behavior.
2. **Shadow:** complete fixed-population comparison and workload-owner approval.
3. **Cohort routing/deadline controls:** enable only approved actions for the named cohort; confirm receipts and manual protections.
4. **Cohort escalation:** enable the bounded escalation profile only after routing/deadline behavior and real-time tests remain healthy.
5. **Supported-profile acceptance:** review the predeclared observation period and operational limits; publish the narrow support statement.

An increase in cohort size or allowed actions is a reviewed binding/policy change, not a hidden runtime toggle. Approval support stays disabled throughout this release. No step grants a React worker identity-resolution or human-voting authority.

### 4.5 Public operational queries and budgets

Provide SQL views/queries and a lightweight dashboard specification; a new web UI or monitoring backend is not required. Include:

| Signal | Definition and use |
|---|---|
| Stale-intent rate | Terminal stale/superseded attempts divided by classified intent attempts over a declared interval; show denominator and zero-sample state |
| Denied/invalid/conflict requests | Separate counts and reasons; distinguish policy/configuration errors from transient failures |
| Overdue-case age | Age relative to the preserved due date for open eligible cases, including cases lacking work |
| Work backlog and drain | Pending/leased/retry/held work counts and oldest age; measure drain after a bounded burst |
| Repeated escalation attempts | Retries of one immutable request versus distinct requests targeting the same occurrence/level; any duplicate applied control is a correctness failure |
| Accepted but unpublished | MDM-owned pending-publication states and their age; not inferred from React work completion |
| Retention coverage | Remaining request-key/receipt/evidence coverage relative to the agreed retry/audit/recovery horizon |

Define operator remediation for each signal. Distinguish absence of data from a zero count. Redact unauthorized details and retain only public correlation references needed for the audit horizon.

Measure representative no-change cycles, bursts, hot-case conflicts, stale-token churn, deadline bursts, backlog drain, restart and populated restore. Record database writes, WAL, storage and measurement conditions. Additional metrics that cannot be captured faithfully are marked unavailable; they do not become supported capacity claims.

Freeze numerical case, churn, queue, latency, retention and recovery thresholds before acceptance. This plan prescribes the method, not fabricated achieved limits. The operator and release owner sign the thresholds after baseline measurements and before the final qualifying run.

## 6. Acceptance tests and release decision

| ID | Scenario | Required result |
|---|---|---|
| T50.01 | Exact final tuple | All common C01–C12 gates pass on the actual release artifact and MDM contract |
| T50.02 | Full fixed-population shadow | No missing/duplicated cases; all comparisons complete within supported bounds; owner accepts expected behavior |
| T50.03 | Cohort boundary | Zero control changes outside approved membership/actions; manual protections remain effective |
| T50.04 | Duplicate/concurrent/stale inputs | Authoritative MDM counts show zero duplicate or unauthorized controls; terminal outcomes and reevaluation are inspectable |
| T50.05 | MDM publication fails after control acceptance | Accepted state remains distinct; no false business-resolution claim or duplicate control delivery |
| T50.06 | Pause during active work | No intent accepted after acknowledged barrier; earlier accepted controls remain accurately reported |
| T50.07 | Populated backup/failed upgrade/restore | Coherent keys, receipts, bindings and publication state recover with matching artifacts; resumption is explicit |
| T50.08 | Clone starts with copied enabled state | Validated deployment guard prevents effects until independent activation; copied row state alone cannot enable it |
| T50.09 | Sustained and burst load | Predeclared workload and numeric backlog/latency/storage/recovery bounds met; no silent truncation or safety degradation |
| T50.10 | Retention boundary | Required correlations remain joinable throughout the agreed horizon; unsafe expiration blocks recovery/admission |
| T50.11 | Core-only upgrade | Ordinary non-MDM policies remain compatible when adapter absent or disabled |
| T50.12 | Optional approvals absent | Initial integration qualifies without MDM M3 and without approval-write permissions |

Pause immediately on unauthorized control, duplicate applied escalation, stale-binding acceptance, unexplained population omission, lost recovery coherence or unexplained capability change. Performance overruns stop expansion and trigger the declared backpressure/pause response; they are not permission to drop cases.

## 7. Migration and rollout recovery

Append the adjacent migration for operational metadata/views only as needed, retaining all earlier immutable data. Execute the documented pause/backup/upgrade/admission/resume sequence against the final stack. Preserve original request keys and body encoding versions.

Back out a cohort by pausing its binding and crossing the barrier. This stops new acceptance, not previously accepted MDM directives. An MDM-authorized reversal, if needed, is a separately audited operation; do not call it adapter rollback. Restore only coherent database/artifact pairs and use the guarded clone procedure for analysis copies.

Release notes state exact supported configurations, numerical limits, known limitations, pending-publication behavior and opt-in status. No broader tenant, RLS, transport, platform or approval support is implied.

## 8. Definition of done and scope cut

R5 completes when the named cohort passes the shared failure suite, full shadow review, controlled enablement and measured observation criteria, with operator and independent release sign-off. The initial stewardship profile is usable and recoverable without approval support.

Cut new dashboard rendering, extra platforms, extra cohort types and nonessential benchmark dimensions first. Never cut full population coverage, real MDM integration, clone/restore drills or numerical acceptance budgets. If partner observation or readiness is delayed, keep the release blocked rather than declaring a fixture demonstration production-qualified.
