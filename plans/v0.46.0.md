The MDM-owned `MDM-STEWARDSHIP/1` interface is agreed and testable. No live routing, deadline-setting or escalation policy is enabled in this release.

## 3. Scope and explicit exclusions

**In scope:** exact-stack identity, an isolated integration environment, a thin public-contract capability adapter, privilege validation, approved contract mapping and shared test fixtures, fresh/upgrade/restart qualification, and installation without a mandatory MDM dependency.

**Out of scope:** replacing React's explicit coordinator with Graph V1; executing MDM graph refresh from React; Delta V1 consumers; WAL CDC; scheduler enablement; live policy consequences; general RLS; multiple administrative scopes; changes to MDM's identity or human-approval model.

The selected stack can contain an MDM-owned, qualified Graph V1 path. React continues to use its existing coordinator and to consume committed local policy tables. Preserve trigger capture, scheduler-off behavior and the existing differential-refresh safeguard unless an independently tested compatibility decision changes them. [S0; S2–S5]

## 4. Implementation design

### 4.1 Stack identity and admission

Capture effective database version, extension versions, artifact digests, platform, isolation, CDC and scheduler configuration. Resolve the reported PostgreSQL 18.3/18.4 discrepancy by obtaining and qualifying the intended artifact, or by an explicit support-boundary decision followed by qualification. Editing the manifest alone is not resolution.

Reuse `pgreact_internal.pgtrickle_capability_report()` and `pgtrickle_integration_status()` rather than creating another parser. Separate the core's explicit coordination mode from MDM's required Graph V1 admission. Recognize the qualified `1.0`, stable, enabled Graph row; allow the enabled Delta row while recording that React does not use it. Reject missing, disabled, or unsupported required Graph capability before adapter effects. An advertised capability must not switch the React coordinator automatically.

Update `require_pgtrickle_runtime()`, `pgtrickle_health_findings()`, their callers, the compatibility fixture, Docker build/runtime pins, and release/qualification workflow assertions together. Append the adjacent SQL migration and regenerate the new install artifact using the existing assembly path. Keep published `0.45.0` SQL and evidence unchanged. Exercise core rules on the new profile before adding MDM effects.

Retain trigger CDC, scheduler off, `READ COMMITTED`, and `pg_trickle.differential_max_change_ratio=1.0`. Leave MDM's candidate-pair FULL workaround in place. Qualify MDM's `pgtrickle.refresh_graph_strict()` on its EXTERNAL members and React's independent explicit refresh on its own members. Test committed policy-table visibility and shared-source interleavings without private CDC access, freshness barriers, or NOTIFY-based delivery assumptions.

Persist only the configuration/contract identities needed to explain admission. Do not mirror pg_trickle private catalogs. Read-only diagnostics must remain useful when MDM is absent. A capability change after deployment must block new adapter effects and require requalification rather than silently changing execution mode.

### 4.2 MDM-owned contract agreement

Freeze the companion's normative section in MDM M0 and record its revision/digest. Confirm `mdm_steward.policy_cases_v1` against M1's installed table and capture exact proposed intent/receipt signatures for M2. The `submit_policy_intent(...)` placeholder is not executable SQL and is absent from `0.11.0`. R0 requires the real read contract; live intent execution remains R2's MDM M2 dependency.

The agreement must settle:

| Contract topic | Decision required for the client |
|---|---|
| Case identity | Non-null unique `case_key bigint`, review identity, occurrence/reopening identity, stability across publication and recovery |
| Deadline basis | Immutable occurrence `opened_at timestamptz`, retained across publication/restore; audited legacy backfill and no automatic deadline for an unknown opening time |
| Action-driving changes | Which revision changes when route, due date, escalation eligibility or relevant evidence changes; audit-only changes must not manufacture actions |
| Concurrency | Expected tokens, stale detection, human override behavior and atomic validation at intent application |
| Automation binding | Scope, enabled state, policy digest, allowed actions/queues/deadline/level limits, replacement and pause linearization |
| Request deduplication | Encoding version, key/body equality, duplicate response, same-key/different-body rejection and retention horizon |
| Receipts | Durable public correlation and the distinction between control application, accepted pending publication and completed publication |
| Permissions | Read, deploy, submit and observe rights; prove the actual React execution role is accepted by MDM role/OID checks without human decision, override, superuser or BYPASSRLS authority |
| Recovery | Coherent restore, clone activation guard, retention horizon and behavior when required prior receipts are unavailable |

These are client acceptance questions, not a competing definition of MDM's schema. Any unsupported mandatory behavior blocks effects and returns to the MDM owner for resolution. [S0 §§3, 6–8]

Configure the existing `pg_react.worker_role` for the restricted automation identity and test the complete worker-to-consequence-to-MDM call path. Do not add another worker merely to bypass MDM's session-role checks.

### 4.3 Fixtures and package structure

Add proposed locations `integrations/pg-mdm/contract/`, `tests/integrations/pg-mdm/contract/`, and `showcase/mdm-stewardship/`. Keep a frozen, provenance-stamped contract copy or approved reference, catalog assertions and shared fixtures.

Fixture rows must include ordinary review cases, a protected manual assignment, tied/no routing candidates, recurrence, stale evidence, a disabled binding and deadline bounds. Put synthetic data in a dedicated test schema/database, not a counterfeit live MDM API namespace. Mark fixture runs as fixture-only. Positive joint qualification must exercise the actual MDM artifact.

## 7. Migration, release and recovery

Append the actual predecessor-to-0.46.0 migration only when implementation changes require it. Package the optional adapter separately from the core dependency declaration. Its installation must default to no effects. Preserve published SQL and ordinary API behavior.

For a changed upstream runtime, stop/pause affected workers, retain a coherent backup with matching binaries and run the exact tested extension upgrade order. Return to the prior coherent artifact/database pair on failure; do not assume a reverse extension migration. Keep existing React coordination until a separately approved migration replaces it.

Publish the qualified environment, raw conformance evidence, unresolved optional capabilities and explicit adapter-disabled state. Update version metadata only when the actual release is implemented and qualified, not when this plan is adopted.

## 8. Definition of done and scope cut

R0 is done when IDENTITY, CONTRACT and required UPSTREAM/MDM-READ evidence pass; the real packaged stack passes its applicable common gates; and the next release can implement a client without guessing MDM SQL. A fixture-only harness is useful progress but cannot close this milestone.

Cut additional platform profiles, extra fixture domains and convenience diagnostics first. Do not cut effective-version checks, normal-role ownership, rollback or the normative contract. If enabling the necessary upstream behavior or building the MDM API is required, stop, record the external blocker, and re-estimate rather than absorbing it into six person-weeks.
