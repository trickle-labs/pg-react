# v0.47.0 — Read-only MDM policy package

> **Status:** Proposed  
> **Predecessor:** `0.46.0`  
> **Source milestone:** R1 — Read-only policy package  
> **Budget:** 30 person-days / six person-weeks  
> **Owners:** Adapter/policy owner; MDM owner reviews mappings; runtime owner reviews public API use; independent reviewer signs no-effect evidence

[Roadmap](../ROADMAP.md) · [Common release gates](../docs/planning/RELEASE-GATES.md) · [Evidence and sources](../docs/planning/EVIDENCE.md)

## 1. User-visible outcome

An authorized policy author can inspect an MDM case, explain its proposed queue and due date, compare a policy replacement over a fixed case population, and export a versioned policy package—without submitting MDM intents or executing command work.

This is the first complete read-only vertical slice, not a production automation release. The source calls for routing candidates, deadline configuration, versioned declarations and existing validate/preview/compare surfaces. [S0 §§4–5]

## 2. Entry gates

The 0.46.0 stack and contract gates must pass. Required policy-case fields, routing permissions, deadline limits, manual protections and recurrence identity must be available in the signed MDM contract. Use one administrative scope and a non-RLS authorized metadata projection; preserve the ordinary unique non-null bigint key boundary.

Use real MDM publication for joint acceptance. Synthetic fixtures support exhaustive tests but do not demonstrate live contract compatibility. No live intent capability is needed by this release, and no write-capable MDM grant should be given to its shadow evaluator.

## 3. Scope and non-goals

In scope are a narrow relational mapping, route selection, proposed due-date calculation, immutable configuration/package versions, side-effect-free comparison, public explanations and a runnable example.

Out of scope are actual `ASSIGN_QUEUE`/`SET_DUE_AT`/`ESCALATE` calls, managed time-only escalation, approvals, general business calendars, network notifications, multiple scopes, RLS support, composite ordinary keys and a new authoring DSL. Additional policy sophistication is deferred rather than hidden in the six-week budget.

## 4. Implementation design

### 4.1 Read only authorized policy metadata

Map the approved MDM projection into adapter-owned condition and candidate views. Retain the MDM `case_key`, original review identity and concurrency tokens required for later work. Do not copy the full review ledger or expose unauthorized raw evidence through explanations.

Validate key uniqueness, nullability, allowed values and contract version before declaring a package valid. Missing mandatory metadata is a blocked case or deployment finding according to the signed contract, never a fabricated default that enables automation. Separate action-driving columns from audit-only fields in the mapping specification.

Proposed files include `integrations/pg-mdm/sql/policy-inputs.sql`, `routing.sql`, `deadline-preview.sql`, and shared contract mapping tests. Names are implementation targets, not installed files.

### 4.2 Routing decisions

Construct candidates from reason code, entity type, approved business metadata, allowed queues and policy applicability. Preserve manual-assignment protection and automation eligibility before a case can produce a would-be control request.

Use existing decision semantics: lowest numeric priority wins; a tie at the best priority is `AMBIGUOUS`; no candidate is `NO_CANDIDATE`. Never introduce lexical queue ordering or row ordering as an invisible tie breaker. A winner requesting the current queue is a semantic no-op. Ambiguous/no-candidate cases remain available for human handling. [S0 §4; S7]

Expose the selected queue, contributing policy revision, applicability, competitors, protection/no-op reason and relevant public case reference through existing explanation results or a thin adapter read projection. Keep the normal authoring journey in public SQL.

### 4.3 Due-date proposal

Calculate a proposed due date from the MDM case creation time and immutable service-window configuration, constrained by MDM's permitted deadline range. Existing deadlines remain unchanged unless an explicitly authorized replacement permits a change.

**Proposed first profile:** elapsed-time durations applied to UTC timestamps, with explicit duration and boundary rules. This narrows implementation effort without claiming support for holidays, business calendars or arbitrary recurring schedules. The policy owner must accept that profile for the named workload; otherwise re-scope before implementation.

Read-only tests use an explicit captured evaluation time as input to the supported evaluation path or fixture relation. Do not invent an `as_of` argument on an existing API. Do not deploy a materialized `now()` predicate and assume time-only liveness; that is the separately qualified 0.49.0 responsibility.

### 4.4 Versioned package and comparison

Use the existing typed declaration/validate/preview/review/compare flow. Include routing rules, deadline configuration and applicability in the reviewed semantic package identity. A configuration update that changes policy meaning must change the policy revision/digest.

Where comparison needs a deployed baseline, provision a non-effecting reference package in an isolated qualification setup. Take pre-call state measurements after setup; the actual comparison must not deploy or mutate lifecycle/work state. Live shadow evaluation must not install command effects merely to obtain a comparison.

For a fixed population, partition cases into supported bounded comparisons with a durable coverage manifest: population identity, capture boundary, key range or explicit membership, policy versions, expected count, observed count and partial status. Prove no gaps/overlaps. If a consistent fixed population cannot be obtained while data changes, run against an isolated consistent copy rather than mixing snapshots. The existing API has no continuation token; do not treat repeated truncated calls as pagination. [S0 §8; S7]

| T47.03 | No candidates | `NO_CANDIDATE`; human handling remains possible |

| T47.07 | Changed service-window or route configuration | Review/package identity changes; stale reviewed declaration is rejected on subsequent deployment tests |

| T47.09 | Partial comparison | Cannot be labeled whole-population safe; complete bounded partitions or isolated qualification resolve coverage |
| T47.10 | Unauthorized metadata or RLS dependency | Rejected without information leakage or privileged workaround |
| T47.11 | Recurring review/publication-only update | Correct case occurrence is retained; audit/publication-only changes do not alter intended route/deadline meaning |

For T47.08 use explicit before/after checks of relevant MDM tables, React work/attempts/lifecycle state and observable refresh boundaries, plus a submission call counter or denied submit privilege. Do not rely solely on the comparison result's selected-state checksum.

## 7. Migration and operational use

Append the adjacent core/adapter migration and include versioned SQL declarations and configuration. Never modify MDM's published schema as an adapter migration. Publish package digests and field mappings with the exact MDM contract revision.

The shadow role gets read-only MDM access and no intent submission privilege. The adapter's write feature remains disabled regardless of whether the database happens to expose the intent function. Upgrades retain this disabled state.

To back out, remove/disable the adapter read-only package through supported lifecycle operations and use the standard coherent restore procedure only if an actual migration failure requires it. There are no accepted MDM directives from this release to compensate. Baseline setup in test databases must be clearly separated from side-effect-free comparison evidence.

## 8. Definition of done and scope cut

The R1 outcome is demonstrated on the real qualified stack and exhaustive fixtures: expected routes/deadlines are explained, every test population is accounted for, and all evaluation remains no-effect. Relevant common gates C01–C05, C09–C12 pass. Live submission tests remain explicitly deferred to 0.48.0.

Cut extra queue heuristics, multiple service-window profiles, convenience views and extra sample domains first. Do not cut tie handling, manual protection, deadline preservation, typed identity, permission checks or complete comparison coverage.
