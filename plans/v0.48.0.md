# v0.48.0 — Durable MDM intent adapter

> **Status:** Proposed; live qualification requires the MDM-INTENT gate  
> **Predecessor:** `0.47.0`  
> **Source milestone:** R2 — Durable intent adapter  
> **Budget:** 30 person-days / six person-weeks  
> **Owners:** Adapter owner and React runtime owner; MDM owner signs transactional/idempotency behavior; independent reviewer focuses on authorization and races

[Roadmap](../ROADMAP.md) · [Common release gates](../docs/planning/RELEASE-GATES.md) · [Evidence and sources](../docs/planning/EVIDENCE.md)

## 1. User-visible outcome

An operator can enable a restricted adapter in a qualification environment, deliver an allowed queue or due-date control through MDM's typed API, and follow the public React work identity to its MDM receipt. Repetition, retry, stale facts and policy replacement are safe and inspectable.

The implementation makes the source's transactional handoff real: **MDM intent submission + receipt correlation + React work completion commit together**. It does not resolve an identity case, send a network notification or execute a human approval. [S0 §§5–7]

## 2. Entry gates

All 0.47.0 read-only evidence must pass. A real MDM artifact must now implement the signed intent API, allowed action validation, atomic binding/token checks, idempotent key/body handling, durable receipts and configured retention. Fixture-only submission is insufficient.

Freeze the request encoding and duplicate-response semantics with MDM before writing production work. Confirm that the installed React typed database-consequence path can keep the MDM call, receipt bookkeeping and completion in a single local transaction. A new external worker or a two-transaction handoff is outside scope.

Both projects must agree on pause/replacement linearization and the behavior of concurrent human changes. Without an atomic MDM-side precondition, a React-side check cannot close the race and live admission stays blocked. [S0 §§6–7]

## 3. Scope

Support only the signed first-profile `ASSIGN_QUEUE` and `SET_DUE_AT` actions. Build reusable typed submission/receipt infrastructure for 0.49.0 escalation, but do not emit escalation yet. Provide per-binding enablement, no-effect/shadow mode, held/withdrawn old work and ordinary public diagnostics.

Exclude arbitrary SQL execution, user-supplied action names, direct MDM table writes, nested `mdm.refresh()`, remote delivery, approvals, general multi-tenancy and a new generic workflow state machine. Keep MDM-specific behavior in `integrations/pg-mdm/`.

## 4. Implementation design

### 4.1 Immutable request envelope

At work creation, persist the complete request body and stable request key. The source recipe is:

```text
binding ID + policy revision + case occurrence + lifecycle generation
+ action-driving revision + consequence identity + escalation level
```

For actions without a level, use the contract-approved explicit absent value. Freeze a typed, versioned, unambiguous encoding with golden vectors; do not concatenate unescaped strings or depend on locale/session formatting. The MDM owner chooses or approves normalization and SQL types. The encoding version is immutable once requests using it exist.

Store public work/policy references, body digest, original review identity and concurrency tokens needed by MDM. Request storage is delivery bookkeeping, not a second review ledger. Retain keys and receipts for the agreed audit/retry horizon. Failure to meet that horizon blocks resume or enablement; it cannot be repaired by silently issuing fresh keys for old attempts.

Persist the key/body before any submission attempt. Retry loads the stored snapshot, never current source values. New policy meaning or a genuinely new action gets new work and a new key. Source/audit metadata that does not change the intended action must not generate a new request.

### 4.2 Typed transactional execution

Use one narrowly scoped wrapper per supported typed consequence or an equivalent allowlisted typed dispatcher. Bind parameters rather than interpolating SQL. Fix the execution search path and qualify object references. The runtime role can invoke only the approved MDM intent operation, not human approval or identity mutation APIs.

Logical execution sequence, not a new public SQL signature:

```text
begin existing React database-work transaction
  load immutable request for the claimed work
  check adapter admission and expected active binding
  submit through the signed MDM intent API
    MDM atomically validates authority, active binding and concurrency tokens
  classify the typed domain result
  record durable public receipt/outcome correlation
  complete or terminally classify this React work item
commit
```

Never put receipt association or completion in an after-commit callback. If receipt storage fails after MDM accepted the call, the local transaction must roll back the MDM change too. Preserve per-job failure isolation so one malformed request does not undo healthy work in unrelated job transactions.

### 4.3 Outcome mapping

| MDM result | Adapter action |
|---|---|
| `APPLIED_CONTROL` or approved duplicate of the same request | Mark delivery complete and retain the original/equivalent receipt; do not label the review resolved |
| `ACCEPTED_PENDING_PUBLICATION` | Retain accepted status and correlation separately from publication; expose only when the selected contract supports this result |
| `APPLIED_PUBLICATION` | Display explicit MDM publication reference; never infer publication from enqueue/completion |
| Stale or superseded | Terminal domain outcome for this immutable request; schedule bounded reevaluation of current case facts |
| Denied, invalid, idempotency conflict | Stop work, expose typed reason, require correction; never retry unchanged invalid input forever |
| Transient database failure or uncertain commit | Existing bounded retry using the identical key and body |
| Unknown result/contract mismatch | Fail closed; preserve diagnostic evidence; require contract correction |

The source supplies the named result categories; exact installed result types must come from MDM. Classify with approved structured outcomes/SQLSTATEs, not English error-message matching. When an API signals a terminal result as an exception, use only the documented transaction/subtransaction pattern needed to retain the terminal work outcome without accidentally committing a partial control change.

### 4.4 Stale work, human edits and replacement

After stale delivery, re-read fresh published facts and tokens through supported React reevaluation. Preserve the old request and outcome. Bound the reevaluation queue; repeatedly stale work must be visible and backpressured, not an unbounded self-triggering loop.

Apply the current policy digest and MDM binding in one supported local deployment transaction. When that is not available, disable the binding, reach the no-new-intent barrier, deploy/validate both sides, then activate. Hold or withdraw incompatible unattempted work. Never rewrite an attempted payload to make it fit the new policy.

Recheck expected binding/digest inside the MDM action's atomic validation. Test a worker racing with pause and replacement: either it is accepted under the old binding before the barrier, or it is rejected afterward. An acknowledged pause does not reverse a control accepted earlier.

### 4.5 Operator surface

Extend the optional adapter's public inspection with work identity, action, delivery classification, MDM receipt reference, policy/binding identity and remediation. Preserve the separation of delivery state and MDM case/publication state. Reuse core retry/recovery operations where their contract fits; do not make operators join private UUID catalogs.

Proposed code targets: `integrations/pg-mdm/sql/request-store.sql`, `intent-consequences.sql`, `receipt-projection.sql`, binding lifecycle mapping and `tests/integrations/pg-mdm/delivery/`.

## 6. Acceptance tests

| ID | Scenario | Expected result |
|---|---|---|
| T48.01 | Same key/body executed repeatedly | One intended MDM control change; stable receipt correlation; completed/reconciled React work |
| T48.02 | Same key with changed body | Contract-defined conflict; no second effect and no mutation of the original attempted request |
| T48.03 | Two workers or duplicate claims | Database claiming plus MDM deduplication prevents double application; attempts remain inspectable |
| T48.04 | Failure after MDM call, before receipt/completion | Entire local effect and bookkeeping roll back; retry uses the original key/body |
| T48.05 | Commit acknowledged ambiguously to worker | Replay reconciles the committed receipt or safely reapplies an uncommitted request; never two controls |
| T48.06 | Human edits queue/deadline or closes case during execution | MDM preconditions determine valid action; stale request cannot overwrite protected current state |
| T48.07 | Binding replaced or paused during execution | No old-policy intent accepted after the new binding/pause barrier |
| T48.08 | Stale request reevaluation | Old item terminal; fresh facts explicitly reevaluated; changed intended action creates new work/key; no endless stale retry |
| T48.09 | Denied/invalid/unknown outcome | No blind retry; bounded, public remediation reason without privileged data leakage |
| T48.10 | Receipt/publication state | Control delivery never labeled business resolution; pending publication remains distinguishable |
| T48.11 | Forbidden execution path | Runtime cannot call human approval/private-write APIs; no nested MDM refresh or network delivery |
| T48.12 | Populated upgrade/restore | Request bytes, keys, receipts, binding identities and ordinary core state remain coherent; effects resume only after admission |

For T48.01/03/05, count MDM's authoritative control changes, not merely completed React work rows. Include actual database disconnect/restart tests, not only mocked exceptions. Apply common gates C01–C07 and C09–C12 as relevant.

## 7. Upgrade and recovery

Append an adjacent migration for request/receipt bookkeeping and adapter metadata. Fresh installations and upgrades leave effect admission off until an authorized operator explicitly enables a tested binding. Existing ordinary non-MDM policies continue operating.

Before upgrade pause and cross the barrier; retain the coherent whole-database backup and matching artifacts. Preserve attempted request bytes and codec versions across upgrades. A new codec applies only to new work and cannot rewrite prior keys.

On failure, restore the coherent React+MDM state and exact prior artifacts using the common protocol. Never restore just one side of the idempotency ledger. An unavailable retained receipt must surface a blocked recovery decision, not automatic key regeneration. Production rollout is still reserved for 0.50.0.

## 8. Definition of done and scope cut

R2 is complete only when real MDM controls, receipt association and React work completion pass atomicity, deduplication, human-edit and policy-race tests. Both permitted actions are implemented behind explicit enablement. All mandatory permissions, retention and recovery decisions are approved.

Cut convenience bulk operations, additional action types and custom dashboards first. Never cut immutable request storage, MDM-side atomic preconditions, uncertain-commit replay or the pause barrier. If the existing database-consequence path cannot preserve atomicity within this budget, stop and split out the required core change with a new estimate.
