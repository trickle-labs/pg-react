# v0.51.0 — Optional approval-policy integration

> **Status:** Conditional proposal; not part of initial stewardship rollout  
> **Predecessor:** `0.50.0` for this proposed sequence  
> **Source milestone:** R4 — Optional approval-policy integration  
> **Budget:** 30 person-days / six person-weeks after external readiness  
> **Owners:** Adapter/policy owner; MDM approval owner supplies normative semantics; security reviewer and operator sign independent admission

[Roadmap](../ROADMAP.md) · [Common release gates](../docs/planning/RELEASE-GATES.md) · [Evidence and sources](../docs/planning/EVIDENCE.md)

## 1. User-visible outcome

An authorized policy can propose approval requirements within limits established by an MDM administrator, and an observer can see MDM-owned approval and publication outcomes through the existing policy/work explanation flow. **Human votes and final approval decisions remain entirely in MDM.**

This release does not turn React into an approval router, voting system or workflow engine. The proposal explicitly makes R4 optional and conditional on qualified MDM M3. It follows R5 here so initial routing/deadline/escalation adoption does not wait for it. [S0 §§1, 5, 8]

## 2. Entry gates: no guessed approval contract

Require MDM M3 or an explicitly approved semantic equivalent to be implemented, installed and independently qualified. Released MDM `0.11.0` has human pair decisions and golden overrides, but no approval proposal, vote ledger, or quorum API. `mdm.preview()` validates or samples definitions; it does not satisfy M3. No later MDM approval release number is assigned. [S9]

Before starting the 30-person-day implementation budget, obtain the exact approval-policy contract, public capability/admission signal, typed proposal operation, administrator limits, authorization rules, proposal/approval revision tokens and outcome projection. None of these missing SQL names/signatures is invented in this plan.

Confirm that 0.50.0's initial integration is qualified and can remain operational with approval support absent. Agreement and review of the supplied approval contract are included below; implementing MDM's voting, quorum, approval ledger or enforcement engine is an external prerequisite, not part of the six-week budget.

## 3. Scope and non-goals

Implement one contract-defined approval-requirement profile demanded by the named cohort, using existing typed declarations, review/compare, immutable work, local intent delivery and receipt correlation. Display the MDM-owned outcome and clearly separate pending approval, accepted control and final publication when the contract exposes them.

Do not add user directories, task assignment, approver authentication, votes, automatic “approve” consequences, parallel quorum engines, segregation-of-duties enforcement in React, deadline-driven auto-approval, a human task UI or network notifications. A timeout may trigger an existing allowed escalation policy; it never implies consent.

Administrator-set minimum protections cannot be weakened by the policy. Approval integration is a separate opt-in binding capability and must not appear merely because the adapter is upgraded.

## 4. Implementation design

### 4.1 Negotiate an independent capability

Add a separate approval-admission check using the MDM-owned published contract. Missing, disabled, unsupported or revoked approval support blocks approval-policy deployment and new approval intents before side effects. It does not disable the already qualified initial routing/deadline/escalation path unless the underlying base contract itself is invalid.

Record the approval contract identity and applicable administrator-policy revision in reviewed declarations/work snapshots as required by MDM. Capability changes invalidate stale approval proposals and require re-review. Do not assume a hard-coded capability string or version until the owning project defines it.

### 4.2 Compare and propose requirements, never votes

Construct a typed proposal for the supported approval-requirement profile from authorized public case metadata. Apply administrator floors/ceilings and applicability during validation and comparison. Repeat authoritative validation in MDM when executing the intent; a successful preview cannot grant permission or defeat a later administrator change.

Use bounded read-only comparisons for candidate changes and preserve whole-population coverage rules. Explanations show why a requirement is proposed and the public constraints that bound it, without exposing protected approver or review evidence.

Version the policy declaration and bind it to the MDM automation policy digest. Use the existing immutable request codec and transactional submission path for the MDM-approved proposal action. Add a new consequence identity only after the action is part of the signed contract. Never overload `ASSIGN_QUEUE`, `SET_DUE_AT` or `ESCALATE` to mean approval.

### 4.3 Preserve human authority under races

MDM validates the active binding, current administrator limits, review/approval revision tokens and current case state atomically. A policy may have been valid at preview time but become stale after a human action or administrator change; return a terminal domain outcome and reevaluate rather than forcing the old proposal through.

Test a human vote/withdrawal or a changed review requirement racing with React submission. React must not mutate the vote ledger or reinterpret a completed MDM outcome. Existing votes must not be copied into React as authoritative state. Requirement changes affecting approvals follow MDM's contract; React cannot invent invalidation or quorum rules.

If MDM cannot provide race-safe enforcement, approval effects remain disabled even if the read-only display is useful. A convenience cache of approver state is not an authorization mechanism.

### 4.4 Read MDM-owned outcomes without feedback loops

Read only the approved outcome projection and retain public correlation references. If the contract exposes them, distinguish requirement proposed/accepted, awaiting human approval, approved/rejected/withdrawn and publication pending/completed. These are semantic distinctions, not invented installed enum literals.

Receipt acceptance is not human approval. An approved case is not necessarily published, and delayed publication is not a reason to cast or resend a vote. An unavailable or stale outcome is shown as unavailable/stale, not as a default approval.

Keep observational approval/receipt timestamps out of action-driving columns. A genuine change to approval requirements can create a new reviewed proposal; an outcome display refresh cannot create recursive proposal work. Retain the minimal public audit linkage under the agreed horizon rather than duplicating full protected approval evidence.

### 4.5 Independent opt-in, pause and recovery

Upgrade with approval admission off. To enable, qualify the independent contract, review the bounded candidate population, verify administrator limits and grant only the narrow proposal privilege. The runtime must continue to lack authenticated human-approval rights.

On approval-capability revocation or pause, hold/withdraw incompatible unattempted approval work, terminally classify stale attempts and retain receipts. Previously accepted requirements or completed human actions remain MDM-owned. The base routing and escalation profile remains independently operable.

Proposed code targets: `integrations/pg-mdm/approval/`, signed contract mapping, typed proposal wrapper, public outcome projection and `tests/integrations/pg-mdm/approval/`. No generic UI or workflow subsystem is created.

## 7. Migration and rollout

Append an adjacent migration for optional approval metadata/projections only after the signed contract is available. Do not migrate or rewrite MDM's approval ledger. Preserve existing request codecs and completed work.

Apply the common pause/backup/upgrade/admission procedure. Separate approval bindings and grants from base adapter enablement. Begin with no-effect comparison, then admit a small explicitly approved cohort for the one supported requirement profile. Use the same exact-artifact, retention and observation discipline as 0.50.0.

On disablement, stop new approval proposals and reach the barrier. Do not reverse accepted requirements or votes. Any MDM-authorized reversal follows MDM's own audited API. Restore coherent state with matching artifacts; do not reconstruct human approval state from React work logs.

## 8. Definition of done and scope cut

R4 completes when the real qualified MDM approval capability supports the bounded profile, runtime authority is demonstrably limited to proposals, human decisions remain MDM-owned, and independent opt-in/revocation/recovery pass. Without MDM M3/equivalent evidence, the release remains blocked and 0.50.0 remains the initial supported integration.

Cut additional approval profiles, richer displays and extra cohort patterns first. Never cut administrator-limit enforcement, human-vote privilege rejection, race-safe stale-token handling or the separation between delivery, approval and publication. Do not expand this release into a general approval/workflow engine.

**After this release:** choose further capability from measured workload blockers. No Delta V1 consumer, general Graph V1 migration, RLS expansion or 1.0 commitment is implied.
