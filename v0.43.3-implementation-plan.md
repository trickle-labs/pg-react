# v0.43.3 implementation plan

Status: planned. Predecessor: `0.43.2`. Release type: correctness patch.
Delivery order and shared release gates are in the [roadmap](ROADMAP.md).
Source findings: F08, F09, F11, F12, F13, F15, and F18 in the
[assessment](pg-react-assessment.md).

## Outcome and boundary

Keep healthy work moving when another job is damaged. Make retry, lease
recovery, and operator output agree with durable state. Prove that a populated
cluster can survive an adjacent update or return to its preceding release
through a consistent backup and the matching image.

Build on the authorization, identity, and reviewed-change fixes in
[v0.43.2](v0.43.2-implementation-plan.md). Preserve SQL consequence atomicity,
lease fencing, ordering, conflict keys, and the existing at-least-once external
delivery contract. This patch adds neither parallel workers nor independent
transaction commits for every job. Start with per-job subtransactions inside
the existing managed cycle.

Keep the return type of name-based lease sweeping and the managed status state
vocabulary. Correct misleading existing fields without replacing public views
or reordering their columns. Richer monitoring APIs require a separate contract.

## Implement the release

### 1. Saturate retry arithmetic before overflow

Replace the live renamed retry calculation, not an obsolete original function.
Cap before narrowing to integer and before multiplication can overflow. Use
bounded numeric multiplication with a pre-multiplication cap check. At most
99 growth steps are needed for the current 100-attempt authoring limit.
Handle multiplier one, a cap already reached, and the largest permitted inputs.
Reject nonfinite or otherwise invalid retry settings at authoring boundaries.

Preserve attempt numbering, error recording, lease release, retry availability,
and final exhaustion semantics. A consequence failure must not turn into an
uncaught arithmetic exception while its handler records the retry.

Gate: a failing consequence with 40 permitted attempts retains the exact capped
RETRY_WAIT delay at attempts 31, 32, and 39, then reaches FAILED at attempt 40
without scheduling another retry. Assert full attempt, lease, and work state.
Also exercise the maximum attempt limit, minimum and maximum caps, multiplier
one, and a very large valid multiplier. Verify exhaustion and no extra effect.

### 2. Isolate each job's validation and execution

Put a subtransaction around one claimed job's validation, consequence, and
completion update. Catch source-shape, executable-definition, dispatcher,
and expired-lease failures at that boundary. Record the affected job's durable
failure or blocked condition outside the failed subtransaction, then continue
with the next eligible job.

Keep the consequence's database writes and its completion marker in the same
subtransaction. On failure, both roll back together. Release or retain leases
according to the existing fenced state transition, never by an unconditional
cleanup that might revoke a newer worker's lease.

Reuse the shared execution path so direct, batch, and managed callers enforce
the same validation. Preserve documented direct-call errors. An invalid worker
identity or token must fail without changing another worker's work. Only the
authorized owner of a claimed job can persist its execution failure.

Use the existing batch bound. Record job failures separately from coordination
failure so successful jobs can commit at the end of the cycle. Audit error
bookkeeping itself for paths that could escape and undo the complete batch.
Do not mask transaction-wide infrastructure failures as successful job handling.

Gate: claim healthy A, damaged B, and healthy C, then change B's consequence
definition. Assert exact committed effects `[A, C]`, B's durable diagnostic,
attempt state, and conflict-lease state. Repeat the cycle and assert no duplicate
committed effects. Repeat for source drift, dispatcher drift, and lease expiry
while an earlier job runs. Cover direct, batch, and managed callers.

### 3. Recover old draining versions through ordinary names

Resolve every authorized ACTIVE, PAUSED, and DRAINING version belonging to the
named rule. Reuse the existing UUID sweep for each eligible version, including
a version whose only remaining work is expired LEASED work.

Preserve `sweep_expired_leases(rule_name text) RETURNS bigint` by summing its
existing recovery results. Keep per-version details inspectable through existing
status and work APIs. Do not change the return type to the assessment's suggested
per-version report in a patch release.

Before normal global claim selection, discover expired leases independently of
PENDING or RETRY_WAIT candidates. Apply bounded recovery to those versions.
Preserve authorization, lease tokens, barriers, and conflict-key cleanup under
concurrent sweeping or replacement.

Gate: lease old work, replace with `DRAIN_OLD`, lose the worker, and expire the
lease. Recover by the public name alone. Assert all old-version state and exact
effects until draining finishes. Repeat with several draining versions, only
expired leases, an unauthorized caller, and concurrent name and UUID sweeps.

### 4. Make status and work fields describe actual state

Inspect `run_result.runtime_state` in `managed_cycle`, including nested policy
results. Map a structured BLOCKED result to the existing `error` process state
and preserve its cause in `detail`. Do not overwrite that result with `ready`
or clear its explanation merely because the process remains alive.

Define when a later successful cycle clears the error. Keep liveness, authoritative
frontier, and execution failures separately inspectable with existing fields.
If work can proceed after coordination is blocked, preserve the blocked
coordination result while recording exact job progress. Test this policy against
barriers rather than treating partial progress as unconditional readiness.

Correct `pgreact.work.claimable` to match due PENDING and RETRY_WAIT state,
eligible rule-version state, and the visible barrier, conflict, and group checks
used by claiming. LEASED work is unavailable to a new claim. Document the field
as advisory because another transaction can claim after a read.

Add a real internal state-change timestamp for rule agenda rows. Prefer one
narrow trigger over edits to every historical mutator if it covers insert,
claim, retry, sweep, requeue, cancellation, blocking, and completion uniformly.
Advance it on a relevant persisted state change, not on a read or no-op update.
Do not derive it from `available_at`, which can be in the future. Expose it through
the existing `updated_at` column without changing the view's shape or types.

For existing rows, retain any provable transition timestamp and mark otherwise
unknown history as NULL. Do not fabricate a historical event at upgrade time.
Document this backfill rule and inspect the decision-work branch for equivalent
semantics. New transitions must provide an accurate value after upgrade.

Gate: compare complete work rows for due and future pending work, due and future
retries, leases, paused and draining versions, barriers, conflict leases, and
terminal states. Verify ordering by real activity and timestamp stability after
no-op updates. Force structured BLOCKED, resolve it, and compare full managed
status and frontier output before, during, and after recovery.

### 5. Replace backup assurance with populated restore evidence

Reuse isolated Compose projects, version polling, log capture, and cleanup from
`tests/m54.sh`. Seed the actual digest-pinned `0.43.2` image with distinct
application roles, standalone rules, package-owned members, decisions, pending
work, retrying work, live leases, a draining version, and committed effects.
Quiesce application writes and worker activity before capturing state. Store
an exact normalized snapshot of declarations, owners, digests, versions, queue
state, attempts, leases, frontiers, and application effects. Keep mutations
stopped until the cluster has shut down and the backup is complete.

Stop PostgreSQL cleanly and verify that it has exited before copying PGDATA.
Archive the stopped volume and checksum the archive. Restart the original
cluster with the candidate image while keeping application writes and workers
quiescent, then apply `0.43.2 -> 0.43.3`. Compare the full state with the snapshot,
accounting only for documented migration changes before resuming activity.
Do not substitute an online `tar` copy or a read-only mount for a consistent backup.

Restore a separate volume using the archived backup and the exact preceding
image digest, with matching PostgreSQL and pg_trickle dependencies. Assert the
old extension version, SQL catalog, application roles, and populated state.
Control worker startup and lease time so background progress cannot race the
initial state comparison. Resume through public recovery APIs and assert exact
committed effects, terminal work, and absence of duplicate database effects.

Add a deterministic failed-upgrade case before the restore. Inject failure in
an isolated test copy of the update script after a catalog or data mutation.
Require the update transaction to leave the old state intact, then perform the
documented backup restore with the previous artifact. Preserve the candidate's
unmodified update as a separate successful case and label injected evidence.

Use SQL assertions that raise on mismatch or compare complete expected output
in the shell. `SELECT false` with `ON_ERROR_STOP` is not an assertion. Verify
that altered expected versions and missing or extra state make the fixture fail.

Gate: both successful adjacent update and failed-update recovery preserve the
specified full state and resume safely. Retain source and target image digests,
backup checksums, state snapshots, execution logs, and final effects. Logical
backup and general failover remain outside this physical-restore claim.

### 6. Make scheduled qualification and failed evidence useful

Remove obsolete schedules from M29, M30, and M33 evidence workflows. Keep a
historical manual lane only with checkout pinned to its matching release tag
or commit and matching image and test expectations. Inspect all schedules for
the same pattern instead of fixing only the two named by the assessment.

Schedule a thin workflow that calls `.github/workflows/qualification.yml` for
current source. Keep release publication tied to that same qualified candidate.
Extend `tests/workflow-syntax.sh` with semantic assertions for checkout revision,
expected extension version, image identity, and selected test profile.

Create the artifact directory before build or test execution. Capture build
output and each test log while preserving the failing command's exit status.
Upload diagnostics and partial evidence with `if: always()` after failed
qualification. Keep success-only image publication and qualified manifests
behind successful execution. Give a failed manifest an explicit failed status
and missing-step list, never a synthetic successful record.

Gate: every scheduled lane has matching source and expectations. Force one SQL
failure and one image-build failure. Assert retained diagnostics and absent
release publication. Historical fixtures remain available without running them
against current identity assertions.

## Qualification and operator documentation

Add planned `tests/v0.43.3.sh` using the preceding release's runner. Carry all
`0.43.2` security, review, comparison, and package regressions into the candidate
gate. Include actual managed-worker cycles and independent external-worker
connections. Mocking only the SQL arithmetic cannot close runtime findings.

Update `docs/operations.md`, `docs/troubleshooting.md`, `docs/backup-restore.md`,
`docs/upgrade.md`, `docs/security.md`, and `docs/api-reference.md`. Turn each
procedure below into an executed qualification fixture with exact results.

| Condition | Required procedure and verification |
| --- | --- |
| Expired lease after replacement | Operator sweeps by name and verifies every draining version and final effects |
| Changed consequence or dispatcher | Operator inspects the blocked job, repairs the definition through the authorized workflow, and verifies safe requeue |
| Source drift or blocked coordination | Operator uses the authorized reconciliation path and verifies frontier progress and cleared error detail |
| Failed upgrade | Administrator restores the stopped-cluster backup with the matching previous image and verifies full state before resumption |
| Retry exhaustion | Operator inspects complete attempt history and explicitly requeues or leaves the terminal result |

Each runbook names the required role, target scope, expected result, and
verification query. Preserve the documented at-least-once boundary for external
effects. Do not turn database-effect assertions into an exactly-once delivery claim.

## Exit gates

- All seven assigned findings have exact-output regressions against the candidate,
  including real managed-worker progress after a damaged job.
- Retry arithmetic remains bounded for every accepted policy. Failure handling
  preserves attempts and fenced leases without undoing healthy jobs.
- Ordinary names recover old draining leases, and work and health output match
  their documented state transitions.
- Fresh install and populated `0.43.2 -> 0.43.3` pass. The matching previous
  artifact restores both the successful-update backup and failed-update case.
- Current scheduled qualification runs matching source and expectations. Failed
  runs retain evidence and cannot publish a release.
- Current docs, API inventory, Rust checks, inherited behavior, and all preceding
  patch gates pass on the exact published image. Remaining cost and scale work
  is listed under `0.44.0`, without a premature production-capacity claim.
