# v0.43.2 implementation plan

Status: planned. Predecessor: `0.43.1`. Release type: correctness patch.
Delivery order and shared release gates are in the [roadmap](ROADMAP.md).
Source findings: F01 through F07, F10, F14, and F16 in the
[assessment](pg-react-assessment.md).

## Outcome and boundary

Make the existing construct, validate, preview, review, deploy, and compare
workflow safe for its intended application roles. A review must describe the
declaration and executable dependencies that deployment actually uses. An
unchanged declaration must compare equivalently after facts change between
runtime refreshes. A valid bounded package must not enumerate billions of paths.

Preserve ordinary signatures and supported JSON preconditions. Keep the current
unsupported-RLS boundary, the managed runtime, and the existing policy model.
Do not add RLS execution support, child replacement semantics for packages,
worker parallelism, or a separate planning framework. Extend the existing
`m54_preview` and package planner where they already own the decision.

Runtime isolation and populated recovery remain assigned to `0.43.3`.
Whole-state comparison checksum cost remains assigned to `0.44.0`.

## Implement the release

### 1. Reproduce failures and fix effective grants

Add an exact signature-to-role expectation to `docs/api-inventory.json`.
Include PUBLIC access, security-definer status, configured search path,
volatility, and ordinary or compatibility classification. Check effective
privileges as well as raw catalog ACLs.

Create one idempotent internal grant synchronizer. Invoke it from installation,
adjacent upgrade, and every `configure_roles` path. Revoke PUBLIC from each
recreated restricted entry point in the same transaction that creates it.
Grant only the inventory's intended matrix.

On role rotation, revoke the managed inventory entries from superseded configured
roles and grant the replacements. Preserve privileges outside that inventory
and independent grant paths. PostgreSQL cannot distinguish a manual grant from
a managed grant with the same object, grantee, and grantor. Document that rotation
revokes that shared entry, while inherited membership or an independent grant
can still confer access. Lock configuration to prevent mixed concurrent rotations.

Use separate login connections for author, operator, reader, and worker tests.
`SET ROLE` does not change `session_user`. A reader that owns a valid source
must still fail an author-only deployment. Test fresh configuration, upgrade
with configured roles, repeated configuration, and rotation in both directions.

Gate: compare the complete effective permission matrix and exact allowed and
denied call results. A matching catalog digest alone does not pass F01 or F02.

### 2. Canonicalize identities before changing fingerprints

Resolve typed `regclass` and `regprocedure` values to catalog components.
Serialize schema-qualified names with PostgreSQL identifier quoting. Include
qualified argument types when serializing overloaded function identities.
Replace the ASCII `schema.object` regex with PostgreSQL-aware parsing and
resolution. Keep value data separate from dynamic SQL identifiers.

Apply this to rule and decision constructors, package support constructors,
validation, export, and import wherever they share identity normalization.
Correct catalog-dependent constructors' volatility to `STABLE` where their
implementation permits it. Do not change the decision constructor's effective
time default silently. Materialize its declaration once in reviewed examples,
or supply one explicit `valid_from` value to every step.

Preserve already stored declaration digests during upgrade. Define normalization
for new declarations without rewriting deployed identity. Old review tokens
must either retain their exact supported meaning or fail with an explicit
re-preview error after the fingerprint format changes.

Gate: the same typed object and explicit declaration values produce identical
normalized JSON and digests under different search paths. Cover duplicate names
across schemas, mixed case, spaces, embedded quotes, and overloaded consequences.

### 3. Share source safety and dependency identity

Reuse the distinct-relation traversal pattern in `relation_query_tree`.
Track visited object identities instead of dependency paths. Validate the full
supported closure before reading caller-selected data, including nested views,
base relations, and relevant function dependencies. Enforce existing structural
limits before expensive traversal and give an exact rejection for unsupported
or unresolvable dependencies.

Reject transitive RLS sources under the existing unsupported-RLS contract.
Define source execution as the authorized application caller, including views
that return `current_user`. Keep privileged catalog inspection in narrowly
scoped metadata helpers. Execute caller-selected source queries outside the
extension-owner definer context. Merely marking an inner helper SECURITY
INVOKER while its caller remains a definer does not change execution identity.

Trace deployment, comparison, simulation, counterfactual, and explanation paths
to the shared policy. Inventory source functions whose bodies or dynamic SQL
hide dependencies. Do not claim that `pg_depend` captures arbitrary function
calls. Reject unsupported source execution before evaluation and document the
supported boundary; consequence review freezes the registered executable
definition and catalog-visible dependencies, not external service behavior.

Extend `m54_source_fingerprint` with canonical dependency identities, nested
view definitions, consequence and dispatcher definitions, ownership, and
security properties that affect execution. Reuse existing executable hashing.
Version this representation and list its inputs in the API contract.

Acquire dependency locks in a deterministic order and revalidate the fingerprint
after the target lock. Prove that relevant concurrent DDL cannot change a bound
dependency between the final check and mutation. For any object category that
cannot satisfy that guarantee, reject reviewed use until it has a supported
locking strategy. An advisory target lock alone does not serialize ordinary DDL.

Gate: direct and nested RLS sources fail before evidence is returned. Benign
identity views agree with direct caller SELECT. Changed consequence bodies,
nested views, dispatchers, owners, or security properties invalidate old tokens.
Include a two-session DDL race, not only sequential changes.

### 4. Enforce replacement guards in the locked plan

Keep `m54_preview` as the ordinary plan representation. After acquiring the
target advisory lock and locking the declaration row, read current declaration,
work, ownership, package membership, and dependency state. Use this state for
both preview decisions and deployment checks, including KEEP.

Centralize supported precondition validation in that path. Preserve the legacy
meaning when `allow_create` is explicitly supplied: true permits creation and
rejects replacing a DEPLOYED target; false requires the expected current digest
when replacing a DEPLOYED target. False still permits creating an absent target
without a digest. Omitting legacy keys preserves M54 stable-name replacement.
Validate types and enforce accepted `expected_current_digest`, `preview_digest`,
and `plan_digest` fields against their documented identities. Specify how combined
fields are checked. Never accept and ignore a precondition.

Derive `old_work_required` from deployed effect-bearing versions and outstanding
work, including COMMAND-to-CONSTRAINT replacement. Require explicit `DRAIN_OLD`
or `CANCEL_OLD` whenever affected work exists. Recheck after waiting for the
lock and apply no implicit drain default in that case.

Gate: create an absent target with `allow_create=false` and no digest. Deploy A,
replace it with B, then reject C with A's expected digest.
Assert that B's full declaration, versions, ownership, and work remain unchanged.
Cover all rule-kind transitions and PENDING, LEASED, and RETRY_WAIT old work
with omitted, malformed, drain, and cancel policies.

### 5. Compare declarations against one fact snapshot

Evaluate both the current and proposed declaration through the same validated
read-only evaluators. Replace the stored-current versus live-proposed pairing
in both rule and decision branches. Resolve each side's own source, key,
selection fields, and parameters from its declaration.

Preserve one PostgreSQL statement snapshot across all source reads under the
supported READ COMMITTED configuration. Audit function volatility and nested
SPI calls to prevent fresh snapshots or volatile source evaluation. Keep the
chosen effective time consistent across both sides. Describe `sampled_time`
and runtime frontier as evaluation metadata, not historical MVCC time travel.
Do not refresh runtime state or create durable temporary comparison state.

Separate match deltas, lifecycle transitions, and executable work projections.
Derive `would_be_work` from the rule kind and transition rather than setting
it true for every proposed row. Apply existing command, constraint, watched-field,
and lifecycle rules. For incomplete evidence, preserve an explicit incomplete
result instead of inferring that omitted rows do not exist.

Gate: pause refresh, insert, update, or delete authoritative facts, then compare
an identical declaration. Assert exact equivalent results for rules and decisions.
Cover nested sources, actual declaration changes, constraints without new work,
evidence truncation, and a concurrent writer between evaluation steps. Compare
full authoritative state before and after each call to prove no runtime effects.

### 6. Bound package processing and make preview truthful

Replace both recursive path walks with one deterministic topological processor
used for cycle detection and preview order. Enforce member, support-object,
edge, and payload limits before graph processing. Process distinct nodes and
edges. A simple in-degree implementation with at most one pass per node is
acceptable at current limits; record its bound instead of claiming unmeasured
linear runtime. Preserve the documented rank, kind, name, and version ordering.

Use the same child action decision in package preview and deploy. Compare
normalized child digests before emitting KEEP. The patch returns a blocking
finding for unsupported changes to package-owned children, including attempts
through a new package version. State the supported removal or version transition
in that finding. Full package-child replacement requires a later explicit
ownership and old-work design.

Gate: test the assessment's 61-node, 118-edge layered DAG, wide fan-in,
disconnected graphs, duplicate edges, and a late cycle. Assert the complete
ordered plan or exact blocking findings. Run the legal graph under a proposed
10-second statement timeout on the pinned qualification runner and retain
elapsed time and temporary-I/O evidence. Calibrate any revision to that ceiling
from a recorded run. A timed-out legal graph cannot count as supported.

## Exit gates

- All ten assigned findings have a reproducer, a fix, and passing exact-output
  regressions against the candidate database.
- Fresh install and populated `0.43.1 -> 0.43.2` produce the same intended API
  permissions and behavior. Historical artifacts remain unchanged.
- Review and comparison pass real-login and two-session tests. Unsupported
  sources fail before executing with broader privileges.
- Legal packages satisfy the recorded graph budget, and every ready unchanged
  package preview can deploy without an intervening state change.
- Current docs, installed API audit, Rust checks, and inherited behavior pass.
  The release artifact is the exact qualified image.
- Release notes identify the token-format transition and the still-open runtime,
  recovery, and comparison-cost findings assigned to the following releases.
