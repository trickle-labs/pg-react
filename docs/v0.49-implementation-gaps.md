## Retention DDL follow-up — 2026-10-31

The focused history-retention lane now blocks non-superuser table owners from
disabling or dropping any of twelve receipt, case, request, attempt and adapter
marker retention triggers, including dropping an adapter-owned attempt table through
`DROP OWNED ... CASCADE`. The event-guard function is owned by a dedicated
no-login role with no memberships and no schema CREATE privileges; the adapter
helper previously removed the event trigger by dropping the function with
`CASCADE`. The current regression rejects both replacement and cascade-drop
of the guard function with exact state preserved. `DROP OWNED BY
mdm_helper_owner CASCADE` is rejected because dropping
`mdm_admin.verify_installation()` would remove a function required by `pg_mdm`;
this dependency check occurs before the DDL guard. The logical-restore lane
also verifies the event guard and all twelve row/TRUNCATE guards are reinstalled
after helper setup and adapter SQL without changing durable history. A separate
marker-mutation regression reproduced helper-owner deletion of the binding
marker before the fix. The current guard blocks marker DELETE, rekeying UPDATE
and TRUNCATE, while preserving ordinary binding configuration updates; the
fresh-install lane verifies exact state and attempts to replace or drop the
marker-guard function. The current merged pg-trickle 0.108.4 logical-restore
run passed all 41 checks, including SAFE capture recovery, pending-work
delivery, and a 91-day case/89-day receipt archive restore with all fourteen
retention guards healthy. An earlier run against a different pg-trickle binary
reported `PGT_EXT_GRAPH_INVALID`; the current 0.108.4 run did not reproduce it.
The archive test backdates timestamps and does not demonstrate 90 elapsed days.
The event guard requires superuser installation and a superuser can still
remove it; operational superuser policy, actual 90-day retention and workload
recovery remain open. Evidence is recorded in the
[qualification note](v0.49-qualification.md#retention-ddl-guard--2026-10-31)
and [DROP OWNED regression observations](../tests/integrations/pg-mdm/evidence/v0.49-history-ddl-drop-owned-current-local-20261031-r8/observations.json),
plus the [isolated guard-owner and pre-restore role regression](../tests/integrations/pg-mdm/evidence/v0.49-history-ddl-guard-owner-isolated-current-local-20261031-r6/observations.json)
and the [owner-preserving cross-cluster logical-restore and recovery checks](../tests/integrations/pg-mdm/evidence/v0.49-logical-restore-cross-cluster-guard-owner-local-20261031-r5/observations.json).

## Confirmed defect and repair

The baseline worker delivered occurrence 1, then continued healthy managed cycles
while MDM occurrence 2 remained at level 1 with no identity mapping, request or
receipt. The regression failed with `managed runtime did not autonomously
enroll/deliver occurrence 3` (`3` is the MDM successor case key, occurrence `2`).

`pgreact_internal.managed_cycle` now invokes the existing optional adapter sync
under the existing coordination lock, before ordinary refresh/time evaluation.
The helper enrolls only cases authorized by both current MDM state and the local
activated binding runtime. It skips existing mappings before identity allocation,
so idle cycles do not consume sequence values or write observation-only rows.
Concurrent insertion retains the existing unique constraint and conflict handling.
There is no new scheduler, occurrence identity, receipt ledger, runtime grant or
activation mechanism. Fresh and adjacent-upgrade SQL are assembled from the same
maintenance input; published predecessor SQL remains unchanged.

## Regression and review boundaries

Run `python3 tests/integrations/pg-mdm/time/audit.py IMAGE OUTPUT --autonomous-recurrence`.
The focused lane creates a real MDM entity through public authoring APIs. It uses
MDM's publication-based resolution/recurrence lifecycle and a selector fixed by
MDM issue identity. The legitimate business removal/reinstatement creates the
successor; no source nudge, manual React refresh/cycle, manual identity sync or direct
escalation submission follows that creation. Authorized human controls set the
due time and initial level. Both level-2 deliveries use the ordinary background
worker at the retained one-claim safety limit.

The test compares complete cases, canonical requests, receipts, adapter/core
attempts, work, unchanged business/selector inputs and historical receipts. It
checks existing public diagnostic output, denied runtime helper/private-producer
access, identity-sequence quiescence, later healthy cycles and a new postmaster
with unchanged durable vectors. MDM remains the occurrence/level deduplication
authority.

The original full audit remains required. Local upstream bootstrap was killed
by signal 9 at `/tests/e2e.sql:3544` before React's integration scenarios; a lower
producer memory cap diagnostic failed there too. Those raw failures are retained,
and the independent focused setup does not replace or weaken the full lane.
The local binaries are Linux amd64 under ARM64 emulation, not a performance
acceptance artifact. Exact results, commands, images and file/library checksums
are retained in the [evidence manifest](../tests/integrations/pg-mdm/evidence/v0.49-autonomous-recurrence/manifest.json),
with compressed complete passing vectors and all retained failures.

The following source-level question was subsequently reproduced and repaired in
the [claimed-work follow-up](v0.49-claimed-work.md): pinned
MDM delivery locks its binding before locking the case, but
`persist_set_policy_binding_state` updates the runtime row without taking that
binding lock. The original artifact applied a new control after pause
acknowledgment. Both pause lock orders now have deterministic native React
coverage on the repaired candidate, along with human edit and replacement claim
orders. Exact dependency adoption and broader release qualification remain open.
